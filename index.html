ROUTE 01

A class is the Pokédex entry. An object is the Pokémon you caught.

The Pokédex page for Pikachu describes every Pikachu: its type, its moves, how much HP it can have. That page is the class. The Pikachu in your party, with its own owner, level and HP, is an object, one instance of that class. Throw a Poké Ball below: the constructor creates a wild Pokémon, and catchPokemon() makes it yours.

The red counter is static int seenCount, which counts every Pokémon ever created, wild or caught. It belongs to the class, not to any one Pokémon, so there is only one copy no matter how many you catch.

Same class, different objects: catch two Pikachu and they share methods (attack(), heal()) but each keeps its own fields (owner, level, hp). this.level inside the constructor means "the level of the object being built right now".
ROUTE 02

Encapsulation: nobody edits your HP directly.

If any code could write pikachu.hp = 9999, the game would be broken (and so would your program). So hp is private, and the only way to change it is through methods that enforce the rules: HP never goes below 0, damage can't be negative, healing can't pass max HP.

Wild Squirtle

hp = 44 / 44

abstract class Pokemon {
    private int hp;          // hidden
    private final int maxHp;

    // the ONLY way HP goes down
    public void takeDamage(int amount) {
        if (amount < 0)
            throw new IllegalArgumentException(
                "Damage can't be negative");
        hp = Math.max(0, hp - amount);
    }

    public int getHp() { return hp; }
    // no setHp(): read-only from outside
}
Why it matters: the "HP ≥ 0" rule lives in one method. Without encapsulation, every attack, item and status effect in the codebase would have to remember the rule, and one of them would forget.

Dashed boxes are abstract: you can't create one directly.

abstract class FireType extends Pokemon {
    protected FireType(int lvl, int hp) { super(lvl, hp); }  // build the Pokemon part first
    @Override public String type() { return "Fire"; }
    @Override protected double effectivenessAgainst(Pokemon t) {
        if (t instanceof WaterType)  return 0.5;   // not very effective
        if (t instanceof DragonType) return 0.5;
        return 1.0;
    }
}
class Charmander extends FireType {
    Charmander(int level) { super(level, 39); }
    @Override public String species()          { return "Charmander"; }
    @Override protected String signatureMove() { return "Ember"; }
    @Override protected int basePower()        { return 10; }
}
super(...) runs first. A Charmander can't exist until its Pokemon part (name, HP, Pokédex count) is built. So the constructor chain is Charmander → FireType → Pokemon, and the bodies run top-down: Pokemon, then FireType, then Charmander.
ROUTE 04

Abstraction: you have never met "a Pokémon".

You have met Pikachu, Squirtle and Dragonite, but never a generic "Pokémon" with no species and no type. Pokemon is an abstract class. It fixes what every Pokémon must be able to do (species(), type(), signatureMove()) and leaves the how to each species.

abstract class Pokemon {
    // a contract: "every species must answer these"
    public abstract String species();
    public abstract String type();
    protected abstract String signatureMove();
    protected abstract int basePower();

    // concrete code that USES the abstract parts
    public void attack(Pokemon target) { ... }
}

Pokemon p = new Pokemon(1, 1);
// ✗ error: Pokemon is abstract; cannot be instantiated

ROUTE 05 · BOSS FIGHT

Runtime polymorphism: one line of code, a different attack each time.

The trainer's loop only knows it has a Pokemon. It calls p.attack(wild), and Java looks at the actual object at runtime to decide which signatureMove(), basePower() and effectivenessAgainst() to run. This is dynamic method dispatch. Pick a fighter and watch where each call lands.

The key idea: the reference type (Pokemon) decides which methods you're allowed to call. The object type (Pikachu) decides which version actually runs. attack() is written once, in the superclass, and still behaves differently for every species.
ROUTE 06

Overloading: the Pokémon Center, a Potion, or a Berry?

All three heal. All three are called heal. They differ only in their parameter lists, so the compiler picks the right one before the program even runs. That's compile-time polymorphism, which is not the same as overriding.

hp = 9 / 44

  public void heal() { hp = maxHp; }                 // Pokémon Center
  public void heal(int amount) {                    // Potion
      hp = Math.min(maxHp, hp + amount); }
  public void heal(Berry berry) {                  // Berry
      heal(berry.restoreAmount()); }               // reuses heal(int)!

ROUTE 07

Interfaces: Fly and Surf don't care about your type.

Charizard is Fire and can fly. Gyarados is Water and can surf. Dragonite is a Dragon and can do both. These abilities cut across the type tree, so they can't live in FireType or WaterType. Java's answer is the interface: a class extends one parent but can implements as many abilities as it wants.

interface Flyable  { String fly(String destination); }
interface Surfable {
    String surf();
    default String describeRide() {    // Java 8+
        return "a smooth ride across the water";
    }
}

// ONE parent, TWO abilities
class Dragonite extends DragonType
                implements Flyable, Surfable { ... }

for (Pokemon p : party)
    if (p instanceof Flyable f)
        System.out.println(f.fly("Cerulean City"));
Type ≠ ability: Gyarados is part Flying-type, yet it can't learn Fly. So "is Flying-type" and "can Fly" are two different questions. That's exactly why Flyable is an interface a class opts into, not something inherited from a type. Gyarados implements only Surfable.
ROUTE 08

IS-A vs HAS-A: a Trainer is not a Pokémon.

It is tempting to write class Trainer extends Pokemon because trainers also "battle". But a trainer has no HP and no type. A Trainer has a party of Pokémon. That's composition: one object holding references to other objects.

Test yourself: inheritance or composition?

class Trainer {                      // NOT extends Pokemon
    private final List<Pokemon> party
        = new ArrayList<>();         // HAS-A
    private static final int MAX_PARTY = 6;

    public boolean catchPokemon(Pokemon p) {
        if (party.size() >= MAX_PARTY) return false;
        party.add(p);
        return true;
    }
}
ROUTE 09 · THE DEEP ONE

Evolution is NOT inheritance.

This is the most common mistake people make when modeling Pokémon in code. It's tempting to write class Charizard extends Charmeleon extends Charmander. Here is why that design is wrong.

✗ The tempting design

class Charmeleon extends Charmander {}
class Charizard  extends Charmeleon {}
  • IS-A fails: is a Charizard "a kind of Charmander"? Then anywhere a Charmander is expected, a Charizard should work (Liskov Substitution). A Charmander-only daycare would accept a Charizard.
  • Objects can't change class. A Java object's class is fixed at new. Your Charmander can't become a Charizard object, but evolution is exactly that change.
  • Charizard gains Flyable, so the subclass would add a whole new ability on top of its "parent".

✓ Better: evolution creates a new object

// in Trainer: build a NEW object, keep owner
public Pokemon evolve(int slot) {
    Pokemon old = party.get(slot), next;
    if (old instanceof Charmander)
        next = new Charmeleon(old.getLevel());
    else if (old instanceof Charmeleon)
        next = new Charizard(old.getLevel());
    else return old;          // final stage
    next.claimBy(name);          // still yours
    party.set(slot, next);
    return next;
}

Charmander, Charmeleon and Charizard are siblings under FireType, not parent, child and grandchild. Evolution is a transformation between objects, which is a behaviour, not a class relationship.

Try it: ritvik.evolve(slot)

Takeaway: use inheritance only when "X is a kind of Y" is true forever. If the relationship can change over time (evolution, a job promotion, a status effect), model it with objects and composition instead.
